# Internationalization

There is no provider and no translation-library dependency. Each component takes an
optional `messages` prop and falls back per key.

```tsx
<Dialog messages={{ "dialog.close": "Fermer" }} />
```

## Why not a provider

The full argument is in [`docs/architecture.md`](../docs/architecture.md). The
decisive point is this: **partial catalogs must be valid.**

When a minor release adds a new message, every existing translation has to keep
working and only the new key needs translating. A context-based dictionary
usually means "replace the whole thing", which turns every new string into a
breaking change for translators. Per-key fallback does not.

The other benefit is SSR: no provider means no locale resolved during render, so
nothing to mismatch between server and client.

## Message keys

Keys are namespaced per component: `<component>.<key>`.

```ts
"common.close": "Close", // shared across components
"example.itemSelected": "{count} of {total} selected", // owned by one component
```

**Renaming a namespace is a breaking change.** `src/i18n/catalog.test.ts` asserts
that every key is namespaced and that documented placeholders match the template.

## Placeholders

`{name}` is substituted at render time. Braces are reserved: a literal brace is
written `{{` and `}}`.

```ts
formatMessage("{count} of {total}", { count: 2, total: 5 }); // "2 of 5"
formatMessage("Hello {{literal}}"); // "Hello {literal}"
formatMessage("Hello {name}", {}); // "Hello {name}"
```

Unknown placeholders render verbatim rather than becoming `undefined`, so a missing
value is an obvious bug in development instead of text a user sees. A substituted
value containing braces is not re-interpreted as a placeholder or an escape.

## Splitting a message across DOM nodes

Values are plain strings, and a component may split one into several text nodes for
placeholders. Each fragment stays addressable and translatable in isolation, which
is better for screen readers and for translation memory than one long
concatenated string.

## Adding a string

1. Add the key to `BASE_MESSAGES` in `src/i18n/base-messages.ts`. This is the
   translation source of truth.
2. Add the placeholder list to `MESSAGE_PLACEHOLDERS`. The test fails if the two
   disagree.
3. Read it with `resolveMessage(messages, BASE_MESSAGES, "yourComponent.yourKey")`.

## Translation workflow

There is no extraction tooling yet. It was left out deliberately: adding i18next or
formatjs at this stage would introduce a runtime dependency for a library whose
premise is that it has none.

When components exist and the key count is real, `formatjs` CLI or
`i18next-parser` can read the source without adding a runtime dependency. The
`BASE_MESSAGES` central catalog means extraction is optional rather than required.

## Dates, numbers and plurals

Not handled by `formatMessage`. Use `Intl`:

```tsx
const count = new Intl.NumberFormat(locale).format(items.length);
const date = new Intl.DateTimeFormat(locale, { dateStyle: "medium" }).format(value);
```

Pass `locale` explicitly rather than relying on the browser default, so server and
client agree.

**Plurals are a real gap and need a decision before the first component that
requires one.** The options are ICU `Intl.PluralRules` with a plural-category
message map, or accepting that plural forms are the consumer's problem. ICU is the
right answer; it is deferred because no component currently needs it and the
contract should be designed with a concrete case rather than in the abstract.
